# GENERATION_REPORT.md

Generated by `engine/report.py` from the frozen files. Every figure below is
read off the data on disk; none is hand-written.

## Why this dataset is synthetic

Razorpay **test mode never produces settlements**. On the captured account
(`merchant_id TShuVt2nlFfcNT`) 15 payments and 2 refunds were created and
captured, the account carried a Rs 23,346.90 balance, and both
`/v1/settlements` and `/v1/settlements/recon/combined` returned `count: 0`
for every month probed. The only forcing mechanism is blocked server-side:

```json
{"error":{"code":"BAD_REQUEST_ERROR",
 "description":"Instant Settlements cannot be created in test mode",
 "reason":"instant_settlements_test_mode_blocked",
 "source":"business","step":"settlement_initiation"}}
```

Reproduced identically through REST, the hosted MCP server and the Razorpay
CLI v1.0.9; a locally built MCP server does not route around it.

**Settlement batching in this dataset is therefore synthesized from Razorpay's
documented behaviour, not captured.** The rule implemented is quoted verbatim
with its URL in `SETTLEMENT_SPEC.md` sec 1. No row claims to be captured
settlement data, and `source_tier` on every row says which tier it sits at.

## Provenance -- `source_tier` distribution

| tier | rows | meaning |
|---|---:|---|
| `captured_real` | 14 | monetary and method facts copied from a real captured payment in `spike/captured_dataset.json`; ids, timestamps and `notes` CONTENT are re-issued, because the captured notes carry spike scenario labels and would leak ground truth |

| `synthesized_modelled` | 139 | statute or standard industry practice; **no Razorpay source** |

`source_ref` on every row names the exact citation. Provenance is only ever
**weakened** by inheritance: a refund against a modelled card payment is
itself modelled, never promoted to its own tier.

### What is NOT claimed

- No settlement batch, and no recon row, was observed. All 12 batches are simulated.
- The fee/tax convention is verified at the **payment entity** level only.
  Whether recon rows carry the same convention is strong inference, not observation.
- Card and UPI were never observed on the captured account (card is WAF-blocked
  on the ajax path; UPI is disabled account-side). Every card and UPI row is
  tiered `synthesized_modelled`.
- Disputes cannot be created through any Razorpay interface -- `POST /v1/disputes`
  is a routing-layer HTTP 404. All dispute behaviour is modelled.

## Method mix

| method | payments |
|---|---:|
| upi | 73 |
| netbanking | 63 |
| card | 41 |
| wallet | 19 |

The captured account produced netbanking x9 and wallet x3 only -- card is
WAF-blocked on the ajax seeding path and UPI is disabled account-side. The
mix here is UPI-dominant by count, as an Indian merchant book is in 2026,
and every card and UPI row is tiered `synthesized_modelled` accordingly.
Card rows exist so `card_network` / `card_issuer` / `card_type` and the
three MDR tiers (2% default, 3% Amex/Diners, 0% RuPay debit) are exercised
rather than dead.

**UPI is billed at 2%, not zero.** Zero-MDR under Sec 269SU binds banks and
system providers, not the aggregator's platform fee, and Razorpay's
published pricing charges it. An earlier draft of this dataset priced UPI
at zero; that was a false claim about a vendor's own commercials and it was
corrected before the freeze.

## Freeze

`DATASET_HASHES.txt` carries the SHA-256 of every data file **and of the
ground-truth key**.

**What it proves and what it does not.** A hash file is *tamper
detection*: it shows the committed data is exactly what the committed
generator produces, so the bytes cannot be quietly hand-edited after the
fact. It is **not** proof of authorship order — a file cannot attest to
what did not yet exist beside it. And because the dataset is a pure
function of one seed, a timestamp could not detect seed-shopping either.
The answer to that attack is `ROBUSTNESS.md`, which shows the planted
classes survive twenty seeds nobody chose.

Verify with `shasum -a 256` against the paths above, or run
`pytest engine/tests/test_determinism.py`, which re-runs the generator from
seed and asserts the committed bytes are exactly what it produces.
