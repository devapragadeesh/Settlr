# corpus/SEEDS.txt -- committed BEFORE any corpus data is generated.

The seeds below are chosen and committed in their own commit, whose message
states that no corpus data exists yet. Only then is the data generated. The
seeds are NEVER reselected and no seed sweep is run: a dataset that comes out
awkward is reported as it is, or a BUG is fixed -- the seed is not changed.

This is the protocol holdout/SEED.txt used (DECISIONS.md 17), for the same
reason: a dataset is not held-out because it is new, it is held-out because
the experimenter could not have chosen it after seeing the result. Points 1
and 2 are verifiable from git log -- this commit precedes every dataset.

# ADDENDUM, 2026-08-24 -- committed BEFORE any of the data below is generated.

The corpus as first built is solvable by a fifteen-line `GROUP BY`
(`corpus/baseline_naive.py`, `CORPUS_SPEC.md` 8): `settlement_id` is populated
on every settled row of every dataset and no dataset ever plants a FALSE one.
Two additions close that, at seeds committed here before either exists. The
original fourteen datasets are NOT regenerated and NOT corrected -- they remain
as they are, and remain reported.

## 1. PSP ABSENCE -- the cell where there is nothing to group by

The recon feed carries no settlement fields at all: no `settlement_id`, no
`settled`, no `settled_at`, no `settlement_utr`, and no `settlement_report.csv`
is emitted. This is not a PSP lying. It is a PSP artefact that is ABSENT --
a second gateway, a historical period predating the recon feed, a bank feed
held alone -- which is the realistic merchant case and the honest justification
for reconstruction. `Reconstructed` is the only positive outcome reachable
there.

## 3. GST/ITC HELD-OUT -- one dataset the resolver+oracle code has never seen

Every `corpus/datasets_gst/*` dataset was generated, inspected, and used to
develop and fix the resolver's ITC-risk flag (§59, §61) and its oracle
measurement (§60) in this same session. Scoring that capability again against
the same two datasets would not be an out-of-sample test -- the code was
shaped, in part, by what it saw there. This seed is for a third GST dataset,
generated after §63's freeze, seen by nobody before the frozen code is run
against it exactly once.

| axis point | family | seed |
|---|---|---|
| A20_B100_Cmax_gst_holdout | datasets_gst_holdout | 20261013 |

Same `weeks=52`, `gst_absent_fraction=1/12`, `gst_no_irn_fraction=1/6`,
`gst_37a_fraction=1/6`, `wrong_attestations=0` as the existing GST spine
point (`A20_B100_Cmax_gst`) -- a comparable population, not a different
experiment, so the held-out result is comparable to §60/§61's numbers
rather than a different question. `20261013` continues the sequential
YYYYMMDD numbering already used for `GST_POINTS`' own seeds (`20261001`-
`20261012`) rather than restarting a new scheme, and is the first unused
value in that sequence -- not picked for any property of the data it
produces, since no data exists yet to have a property.

Same protocol as points 1 and 2: never reselected, no sweep, an awkward
result reported as it is or a bug fixed -- but per `DECISIONS.md` §63/§64,
"a bug fixed" means only in `corpus/generator/` itself if generation fails
its own leak/triviality audits (as happened once for the noisy GST dataset),
never in `resolver/`, `resolver_contract/`, or `corpus/oracle.py` in response
to what the held-out SCORE says.
