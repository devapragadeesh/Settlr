## What this is

The **Settlement Truth Engine** — a Razorpay AI Buildathon (Track 04) submission
that reconciles a payment ledger against a bank statement, ERP orders and
GSTR-2B. The repo is a hiring artifact: it will be cross-examined by engineers,
so **evidence discipline matters more than features**. Numbers are produced by
scripts from live runs, never hand-written into markdown.

## Architecture

Four packages with a **strictly one-way dependency**, which is the load-bearing
structural property of the whole repo:

```
engine/     generates the data and the isolated answer key
matching/   the solver — must never read the answer key
eval/       the ONLY package permitted to read the key, scores matching/
holdout/, scale/   additional datasets, generated by driving engine/ as a library
```

**`engine/`** — `simulator.py` implements `SETTLEMENT_SPEC.md` (a normative
document; every rule is tagged with a provenance tier) and nothing else.
`generator.py` builds the ledger, plants 15 classes of hard cases, and emits
both the solver-visible data and `ground_truth/ground_truth.json`.

**`matching/`** — a 4-stage cascade, `cascade.run(dataset, llm=...)`:

1. `stage1_exact` — join `settlement_id → UTR`, `order_id → invoice`
2. `stage2_fuzzy` — `(amount, date)` fallback for broken join keys; proposes ERP
   candidates and **refuses** them all for want of a shared identifier
3. `stage3_solver` — CP-SAT subset-sum reconstruction of each bank credit from a
   pool, with the settlement columns *withheld* from the enumerator, plus a
   Hungarian ERP residual
4. `stage4_exceptions` — deterministic classification; the LLM narrates and
   never matches

`matching/model.py` is where the design intent lives: `Ambiguous` deliberately
has **no `decomposition` attribute**, so a confident answer on an ambiguous
batch is unrepresentable rather than discouraged. `resolve_from_candidates` is
the only constructor of a `Resolution`.

Both `loaders.load(dir)` and `cascade.run(dataset=...)` are parameterised, which
is how `holdout/` and `scale/` reuse the frozen solver without touching it.

## Invariants that are easy to break

**Frozen paths.** `engine/data/*`, `engine/ground_truth/*`, `engine/simulator.py`,
`engine/generator.py`, `engine/DATASET_HASHES.txt` are frozen at commit
`f7a6450`. The cascade is frozen at `81c04e0`. New datasets are **new files in
new directories**; the generator is driven as a library with its module-level
constants rebound on the imported module object, never edited on disk.
`tests/test_holdout_freeze.py` hashes all nine paths around a live generation
run and asserts equality.

**Ground-truth isolation** is enforced two ways, and both must keep passing:
`engine/tests/test_no_leakage.py` scans `engine/`, `matching/` and `eval/`
against a repo-relative-path allowlist, and `tests/test_isolation.py` enforces
the same over `matching/` by AST. Any new `eval/` module that reads the key must
be added to `GROUND_TRUTH_ALLOWLIST`, and no `matching/` module may ever appear
there.

**Held-out protocol.** `holdout/SEED.txt` was committed in its own commit
*before* any data existed — that ordering is the evidence and is visible in
`git log`. The seed is never reselected, no sweep is run, and the solver is
never tuned in response to held-out results.

**Metric definitions** live in `DECISIONS.md` §12 and are shared by both eval
reports via `eval/metrics.py`. Match rate excludes rows that correctly have no
bank credit; precision/recall are over determinate batches only; mean candidate
set size is reported alongside `truth_in_candidates` to close the
"enumerate more to score better" loophole. Do not redefine these per-report.

## Known open defects — do not trust `Determinate`

`investigation/DEFECT_REPORT.md` records three measured, unfixed defects. This
matters for any work that reads or reports Stage 3 output:

- **D1** — `Determinate` means "unique among subsets *maximising applied
  debits*", not "unique closing subset". Two primary-set credits had 3 closing
  subsets each and were reported `Determinate`. The objective can actively
  select a wrong subset.
- **D2** — `stage3_solver.run` consumes pool rows on an uncorroborated
  `Determinate` (the `elif` branch). This caused 50 mis-placed rows on held-out
  data and is unreachable on the primary set.
- **D3** — `Ambiguous.certain_rows` assigns rows uncorroborated too; any
  `Determinate`-scoped guard misses it.

`Determinate.__post_init__` **cannot fire** — every candidate satisfies
`sum == target` by CP-SAT construction, so the residual is identically zero.
"balance-identity violations: 0" is not evidence of correctness.

A fix is a deliberate, recorded decision with its own validation, not a patch
applied while doing something else.

## Conventions

- **Money is integer paise everywhere.** No float arithmetic. Rupee strings are
  parsed by `matching/money.py` with integer ops on the decimal string.
- **`DECISIONS.md` is append-only and numbered**, and every entry carries its
  *rejected* alternatives with the reason. Adding a decision without recording
  what was rejected defeats its purpose — the panel round grades justification.
- Reports are generated. If a number appears in a markdown file, a script in
  `eval/` should have written it.

## The benchmark corpus and the resolver contract

The frozen primary dataset is **demoted, not deleted**: it is the easy
regression baseline, the case where the answer is over-determined and any sound
resolver must score near-perfectly. Its data defects are documented findings.

```
resolver_contract/   the outcome vocabulary. INTERFACE ONLY, no algorithm.
                     Committed BEFORE any corpus data existed (see git log).
corpus/generator/    parameterised, seeded, deterministic dataset family
corpus/datasets/     14 axis points, each with its own key, hashes and report
corpus/leakage_audit.py   searches for leaks; validated against the frozen set
corpus/oracle.py     scores (resolver_output, ground_truth) only
```

```bash
python3 -m corpus.generator.build --list      # the axis points and their seeds
python3 -m corpus.generator.build --all       # regenerate (slow, ~25 min)
python3 corpus/leakage_audit.py --validate-frozen   # must rediscover D4-D7
python3 corpus/leakage_audit.py --all         # gates the build
python3 corpus/baseline_old_engine.py --all   # the frozen cascade vs the corpus
pytest corpus/tests -q
```

**Ordering is the evidence, and it is verifiable from `git log`:** contract →
seeds → datasets → baseline prediction → baseline results. Seeds are never
reselected; when a dataset comes out awkward, a *bug* is fixed.

### Things that are easy to get wrong here

- **`corpus/generator/sim.py` re-implements only the batch-formation loop** and
  imports every arithmetic primitive from the frozen `engine/simulator.py`.
  `corpus/tests/test_conformance.py` asserts exact equality with the frozen
  simulator; if it fails, the corpus stopped being comparable to the frozen
  numbers.
- **`corpus/generator/bank.py` must never be passed a settlement identifier.**
  `Payout` carries an amount and a timestamp. That signature *is* the D4 fix;
  the tests only corroborate it.
- **No row may ever be minted to make arithmetic work** (D5). Ambiguity is
  `planted: false` everywhere by construction — it falls out of a price
  lattice. If a target is unreachable, record `planted: false` with a reason.
- **Ground truth records `composition` and `closure` separately.** A resolver
  returning a confident answer where `closure.count > 1` is wrong *even when it
  matches* `composition`, because it cannot have known.
- **`resolver_contract/RESOLVER_CONTRACT.md` §6.4 is a dated amendment.** Any
  further change after this point must be dated the same way, or the
  contract-before-corpus claim stops meaning anything.
- **Do not write the resolver in the same change as corpus work.** Building
  both together is how the resolver ends up shaped to the corpus.
